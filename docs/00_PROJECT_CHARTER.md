# Mongol AI 项目宪章：我们到底在解决什么

**状态**：最高优先级项目事实源  
**版本**：1.0.0  
**生效日期**：2026-08-08  
**适用对象**：产品、工程、研究、设计、测试人员与 AI Agent

> 如果你刚刚克隆本仓库，只先读这一篇。任何路线图、历史报告或实现与本
> 文冲突时，以本文为准，并修正文档或实现。

## 1. 一句话目标

建立一个**不依赖浏览器碰巧选中哪个字形、不依赖单一字体或输入法作为裁判**
的传统蒙古文计算与渲染引擎：输入什么，系统就无损理解什么；根据明确规则
确定字形；自上而下书写；列从左向右推进；结果可复现、可解释、可测试。

它不是普通网页加一条 `writing-mode`，也不是更换字体后“看起来差不多”。

## 2. 问题的本体

传统蒙古文数字显示可以拆成一个确定性计算问题：

```text
原始输入序列
  → 输入协议解码（Unicode / Onon MN / 经授权的其他编码）
  → 无损语义表示
  → 字母与控制符解析
  → 词内连接状态计算
  → 变体意图计算
  → 语义字形选择
  → 连接几何与竖向排版
  → 可见轮廓 + 可复制的原文
```

核心函数可以写成：

```text
glyph = f(base_letter, joining_state, variation_intent,
          word_context, rule_version)
```

其中：

- `joining_state` 至少包含 isolate、initial、medial、final；
- `variation_intent` 可以来自 FVS、MVS、词法条件或输入协议；
- FVS、MVS、ZWJ、ZWNJ、NNBSP 是计算信息，不是正文中需要绘出的字形；
- 渲染结果必须保留到原始码位的可追踪关系。

## 3. 不再误设的问题

以下事情不是引擎开始工作的前置条件：

- 等待某位专家批准每一个字形；
- 寻找或制作一张所谓“正确截图”作为字形答案；
- 先判断 Noto、Onon、蒙科立或 Unicode 谁是唯一真理；
- 等 Unicode 组织补完所有规则；
- 让用户填完一百条审核表；
- 找到一款在所有平台上都恰好正确的现成字体；
- 把浏览器或 HarfBuzz 的默认输出直接称为正确答案。

真实蒙古文网页语料、人工、输入法、字体、论文和标准都可以贡献证据，但都不
拥有“阻止引擎继续构建”的权力。争议应成为版本化测试和待求解规则，不能变成
无限期阻塞。

## 4. 第一性原理

### P1 — 原文不可丢失

保存用户实际提交的码位序列。不擅自归一化，不删除控制符，不猜测 PUA，
不把 NNBSP 改成普通空格。

### P2 — 编码、语义和轮廓分层

同一语义可能来自不同输入法或编码；同一码位序列也可能在不同上下文选择
不同字形。三者必须分开建模：

```text
输入编码 ≠ 语义字形 ≠ 最终轮廓
```

### P3 — 规则先于后端

Unicode、OpenType、HarfBuzz 和字体是后端能力或证据来源。项目自己的语义
规则决定“需要哪个字形”，后端只回答“能否提供”。后端不能提供时，应进入
项目自有字形层，而不是静默显示错误结果。

### P4 — 控制字符不可见

FVS、MVS、ZWJ、ZWNJ 等控制符参与解析和选择，但不得作为正文轮廓绘制。
调试层可以显示其码位、作用和处理结果。

### P5 — 原生竖写

阅读方向必须自上而下，列必须从左向右增加。布局系统处理的是连接后的字形
流，不是把一行横排文本整体旋转后冒充竖排。

### P6 — 确定性与可复现

相同原文、规则版本、字形资产版本和布局参数必须得到相同结果。每个结果都
能追溯到输入码位、语义角色、规则和轮廓。

### P7 — 证据不等于裁判

Unicode 描述编码意图；Onon、蒙科立和字体展示实现选择；母语者提供真实用法
证据；数学断言验证一致性。它们相互交叉验证，不以单一来源垄断系统真值。

### P8 — 从真实文本中学习，不从截图抄答案

项目通过爬虫采集公开传统蒙古文网站中的**原始文本序列及其上下文**，形成可
统计、可搜索、可重放的网页语料。核心证据是码位、词边界、上下文、出现频率、
来源 URL、采集时间和页面语言元数据，不是截图。

截图只可用于页面布局和视觉回归，不得作为语义字形规则、编码映射或正确轮廓
的事实源。图片中的像素无法可靠还原原始字符、控制符和输入意图。

## 5. 引擎内部对象

下一代语义层的最小记录应类似：

```json
{
  "source": {
    "profile": "unicode-national",
    "codepoints": ["U+1820", "U+180C"]
  },
  "character": "MONGOLIAN_LETTER_A",
  "joiningState": "medial",
  "variationIntent": "third_form",
  "semanticRole": "MONGOLIAN_A.medial.form3",
  "ruleSource": ["unicode-17-standardized-variants", "mongol-ai-rule-v1"],
  "backend": {
    "status": "supported | substituted | project-glyph-required",
    "glyphAsset": null
  }
}
```

glyph ID 只属于具体字体版本，不能代替 `semanticRole`。不同字体可以为同一
语义角色提供不同风格的轮廓。

## 6. 外部系统的正确位置

| 来源 | 在本项目中的角色 | 不是 |
|---|---|---|
| Unicode | 码位、标准变体和控制语义的基线 | 完整字形轮廓库 |
| W3C | 书写方向和网页排版要求 | 字形真值库 |
| Onon MN | 真实输入提交及候选行为的观测源 | 必须嵌入的闭源依赖 |
| Onon MK/MW、蒙科立 | 其他编码生态的观测与未来适配源 | 可以猜测转换的黑箱 |
| Noto/其他字体 | 可复现轮廓后端和差分对象 | 自动正确的语言裁判 |
| HarfBuzz/OpenType | 可利用的塑形执行后端 | 项目语义模型本身 |
| 母语者/文字工作者 | 真实用法、审美和误差发现者 | 每次开发的审批机关 |
| 公开蒙古文网站 | 大规模真实码位序列、词境和频率的语料来源 | 可整站复制再发布的免费内容 |

不得复制或再分发未经许可的商业字库轮廓。可以研究其输入输出行为，在许可
允许的范围内建立独立规则和原创／兼容许可的字形资产。

网页采集遵守站点 robots、访问条款、限速和版权边界。仓库优先保存来源清单、
哈希、结构化特征、短测试片段和可重建脚本；只有许可明确的完整正文才能再分发。
这些要求约束采集方式，不把公开网页语料研究变成审批流程。

## 7. 当前仓库已经完成什么

截至 2026-08-08：

- 原文逐码位保存，FVS/MVS/NNBSP/ZWJ/ZWNJ 不被静默删除；
- 锁定 HarfBuzz WASM 与 Noto 字体哈希，可生成确定性 SVG path；
- 控制字符的调试证据与生产绘制已经分离；
- 建立 100 条种子任务和 234 个上下文差分探针；
- 93 个 Unicode 声明位置参与机器断言，141 个位置仅观察；
- 当前字体后端对 16 条标准变体没有产生预期差分，MVS 尚需词级上下文；
- GitHub Pages 提供引擎实验室和证据检查界面。
- S2.0 已把93个 Unicode 声明目标转换为稳定 `semanticRole`；当前后端75个具体目标可响应、18个具体目标需要项目字形；
- S2.0 网页语料管线已能检查 robots/TLS、限速抓取、无损提取控制符并生成码位统计。
- S2.1 已锁定 Unicode 17.0.0 `Joining_Type`，普通蒙古文单词无需注入 ZWJ 即可计算 isolate／initial／medial／final；连接边界、透明选择符和促连字符均有自动断言。
- S2.1 已将 MVS／NNBSP 结构事件与连接状态分层，并生成不含正文的网页控制符共现索引；当前真实观察为 FVS2 1次、MVS 0次、NNBSP 0次。
- S2.2 已为18个项目字形缺口建立入口、出口、推进量、边界框、路径安全和许可证合同；当前轮廓资产0／18就绪。

这些数字描述**当前后端的可观察行为**，不代表“83 个字已经被专家批准”，
也不表示开发必须停下来等待批准。

## 8. 当前阶段：S2 语义字形计算引擎

S2.0 Foundation 与 S2.1 Context Model 的确定性连接状态、控制符结构层已经
落地；当前进入 S2.2 Geometry Contract，构建可验证的项目字形资产和组合接口。阶段事实与
未完成边界见
[`PHASE_S2_SEMANTIC_GLYPH_ENGINE.md`](05-project/PHASE_S2_SEMANTIC_GLYPH_ENGINE.md)。

S2 的目标不是继续扩大人工审核表，而是让引擎拥有独立的语义决策能力：

1. 建立 93 个标准目标的 `semanticRole` 注册表；
2. 实现连接状态和变体意图解析器；
3. 建立后端适配接口，测量字体能否实现所需语义角色；
4. 对缺失角色进入 `project-glyph-required`，不再无声退回错误字形；
5. 建立连接入口、出口、基线、推进量和边界框的几何断言；
6. 建设公开传统蒙古文网站爬虫，统计真实序列、控制符和词级上下文；
7. 用 U+1820 + U+180C 的 medial third form 作为第一条纵向切片；
8. 完成后扩展至其余标准变体、MVS、词级规则和多列布局。

S2 的第一条验收不是“有人点了同意”，而是：

```text
给定相同输入与上下文
→ 得到唯一 semanticRole
→ 后端支持状态明确
→ 控制符不绘制
→ 轮廓连接几何通过断言
→ 输出与原文可双向追踪
```

## 9. 产品边界

本项目首先解决传统蒙古文的数字输入、语义塑形和竖排显示。OCR、语音、翻译、
大模型对话、拼写和语法可以在此基础上发展，但不能抢在底层文字表示正确之前
成为主线。

我们不承诺尚未测试的语言准确率，也不因谨慎声明而停止底层工程。正确做法是
同时保存：规则结论、证据来源、反例、实现版本和已知边界。

## 11. 不可回退条款

- 不得重新把 CSS 竖排成功等同于蒙古文字形正确；
- 不得重新让单一字体、输入法、专家或标准成为唯一裁判；
- 不得把“正确截图”当作编码或语义字形事实源；
- 不得把控制字符画进正文；
- 不得以“尚未审核”为由停止构建可验证的语义规则；
- 不得在缺少授权时复制闭源编码表或字形轮廓；
- 不得隐藏冲突、猜测转换或伪造准确率。

本宪章可以随证据升级，但改变上述方向必须在提交中明确说明原因、影响和替代
模型，不能通过局部实现悄悄改回旧路线。
